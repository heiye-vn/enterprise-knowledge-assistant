# 模型网络配置与失败恢复

2026-11-15：完成增强待办第一项。模型调用改为明确的连接策略，千问与三方回答可分别设置；新增脱敏诊断和用户主动重试。未修改 macOS 全局代理、模型型号或 API Key。

## 排查证据

历史记录曾观察到 macOS 系统代理引起本机与 Worker 的调用差异。本轮复验时系统代理地址已经变化，默认代理与直接连接的千问请求都成功，因此不能断言本轮仍在复现全部历史故障。

在独立测试进程中模拟不可用 HTTPS 代理后，继承代理的向量调用超时，直接连接成功；证明默认继承网络配置会让模型请求受不可用代理影响。模拟只设置了测试进程环境，没有修改系统设置。

同时发现当前三方服务直接连接连续失败，而继承当前系统代理后普通和流式回答成功。因此分别配置网络路径，避免用统一直连修复千问时损坏三方模型调用。

## 配置与诊断

- `KH_MODEL_TRUST_ENV=false`：默认直接连接，应用于千问的向量、重排、意图判断和回答。
- `KH_MONKEY_MODEL_TRUST_ENV=true`：本机三方回答继承系统/环境代理；省略该项时沿用上一项。容器不会读取宿主机的 macOS 系统代理，如果需要容器调用三方服务，必须另外配置容器可访问的代理地址。
- 保持 TLS 校验开启，不自动改提供方或切换模型，不自动重发生成请求。
- 每次请求记录提供方、`operation`、连接模式、耗时、HTTP 状态和失败类别。聊天区分 `intent` / `answer`，同时覆盖 embedding、rerank、chat 和 chat_stream。
- 网络失败类别包括代理、DNS、TLS、连接/读取/发送超时、连接池及协议中断；限流、认证和服务端错误保留独立业务错误码。日志不包含 Key、原始错误文本、提示词、文档内容或代理凭证。
- 成功诊断使用 INFO，失败使用 WARNING；前端只显示简洁原因。

更改配置后重启 API；任务客户端代码或 Worker 配置变更时执行 `docker compose build worker` 和 `docker compose up -d --no-deps worker beat`。私有 `.env` 已设置本机验收通过的两项值，权限保持 0600。

## 手动重试

失败回答在最后一条消息处提供“重试回答”，仅允许可恢复错误，总共最多 3 次尝试。重试沿用原 user/assistant 消息、请求 ID，并显式增加 `retry_attempt`；同一尝试重复提交或并发提交不会重复生成。旧问题在新消息出现后不能重试，以免修改后续上下文。

`POST /api/chat` 保留原请求格式，主动重试额外提交 `retry_attempt=2|3`。不带该字段重放失败请求不会重新调用模型；成功请求重放仍返回已保存结果。消息接口增加 `client_request_id`、`attempt_no`、`max_attempts` 和错误 `retryable`。

结果写入检查消息状态、当前尝试号和有效期，过期旧请求不能覆盖新尝试。无需数据库迁移。网络响应丢失后页面读取已保存消息并继续轮询，受控重试不重复添加用户问题。
