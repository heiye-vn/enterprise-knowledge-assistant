# 意图识别、澄清与检索详情

本文说明三类意图路由、澄清和持久化的检索详情。界面面向电脑端，历史记录以本轮实际执行数据为准。

## 路由与澄清

- 路由使用现有回答模型，扩展为通用对话、知识库问答、需要澄清三类。模型输出经过结构校验；企业内部事实误判为通用问题时，继续使用已有的依据保护规则转入检索。
- 只有具体判断缺少必要条件或指代不清时才澄清。历史已有条件不重复问，询问整体流程或所有金额档位时直接检索；资料缺失不以反复澄清替代拒答。
- 澄清作为正常回合保存，继续追问可补全检索问题，也可切换通用话题。澄清不携带文档引用，不增加业务表或答案状态枚举。
- 每条新助手消息下提供默认折叠的“检索详情”或“问答过程”，展示本轮实际路径、补全后的检索问题、服务端处理耗时、阶段状态及降级提示。不展示模型内部思考。

## 分数与候选

| 字段 | 说明 |
| --- | --- |
| BM25 | 关键词召回得分；保留实际数值，包括负数。未命中显示“未命中”。 |
| 向量距离 | pgvector 余弦距离，越低越接近；不改造成虚假的百分比。 |
| RRF | 多路排名融合得分，展示融合排名。 |
| Rerank | 所有实际参与重排候选的相关性分数和重排排名；失败或超出输入预算不伪造分数。 |

聊天默认每路召回最多 30 个候选，融合后最多保留 30 个；重排沿用 28000 字符预算，返回最多 6 个结果用于后续判断。独立检索接口仍按 `top_k` 调整原有候选上限。界面分别显示两路召回数、融合总数、参与重排数和返回数。融合列表被截取时，展示候选数与融合总数可能不同。

区分三个概念：入选的检索结果、实际送入回答模型的片段、通过答案引用校验的最终引用。相关性不足直接拒答时，即使已有候选，也不会显示为“已送入回答”或“实际引用”。低分拒答沿用现有 0.25 判断，没有借展示功能修改阈值。

候选卡片显示有限摘要、章节、来源、分数、融合/重排排名和使用情况。默认展示前 6 个，其余候选另行展开；可直接打开固定 job 的正文或定位实际切块。标题中的 Markdown 强调正常显示，切块摘要保持实际内容。

## 保存、失败与兼容

使用现有 `ChatMessage.request_snapshot.details` JSON 保存版本为 1 的记录，查询消息时返回 `details` 和 `warnings`。候选摘要最多 800 字符，正文仍从原有来源接口读取；没有新增数据库表或迁移。

阶段使用 `completed / failed / skipped`，未执行阶段的耗时为 null。澄清可以随意图调用返回；当前 SSE 通用回答另行调用模型流式生成，详情按实际调用记录阶段，不伪造独立生成调用。耗时为本次服务端核心处理时间，不包含浏览器网络往返或消息创建事务；小于 1ms 的阶段显示为 `<1 ms`。

完成、拒答和模型失败均保存已经实际获得的详情；原消息重试会重新生成本轮记录，前端也清空旧的临时详情。已有历史消息没有记录时不补造数据。展开详情或刷新会话不会重新检索，检索分数和候选保持不变。
